# Fix: /harness spawned wrong executable

## Symptom
`/harness` in the editor failed with:
`error: unexpected argument 'do' found` / `Usage: ee-agent-opencode [OPTIONS]` (exit 2).
A later retry in a restored memory-only session failed with:
`` `/harness` needs a completed task in this session; run the task first ``.

## Root cause
`crates/ee-agent-orchestrator/src/provider_adapter/harness_command.rs` used
`std::env::current_exe()` and then prepended `do agent harness improve`.
The provider process is `ee-agent-opencode`, so the CLI subcommand was passed
to the provider binary and clap rejected it.

## Fix
- Added `resolve_ee_executable()` with precedence:
  1. `EE_CLI_BIN` env override (must be an executable file)
  2. `ee` sibling of the running provider binary
  3. `ee` found on `PATH` (empty PATH components skipped)
- Added `last_logged_task()` fallback: when the in-memory model transcript has
  no task, replay the runtime session log and reuse `last_task`.
- Added regression tests for sibling resolution, override, PATH fallback,
  missing executable, empty PATH, and logged-task fallback.

## Validation
- `cargo test --quiet -p ee-agent-orchestrator provider_adapter::harness_command` - 9 passed
- `cargo test --quiet -p ee-agent-orchestrator` - 1493 + 8 + 8 + 7 passed
- `cargo clippy --quiet -p ee-agent-orchestrator --all-targets --no-deps -- -D warnings` - clean
- `cargo build -p ee-cli -p ee-agent-opencode` - success
- `target/debug/ee do agent harness improve ... --dry-run` - printed plan

## Caveat
Restored sessions with memory-only session logging still lose provider task
history across process restart. The logged-task fallback only helps when
durable session logging (`--session-log-dir` / `session_log_durable`) is
enabled. In a restored memory-only session, run a task before `/harness`.
