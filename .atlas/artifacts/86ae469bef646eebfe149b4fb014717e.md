# Plan: close deferred boundaries in ISSUES.md 700-701

## 1. ACP v2 per-command interception (deferred)

Hard constraint: ACP v2 `session/request_permission` carries `CommandPermissionSubject { command, cwd, tool_call_id, terminal_id }`, but the agent executes the command itself. There is no client `terminal/*` method in v2. The host can only allow/reject; it cannot wrap the exec.

Therefore per-command containment without an agent-process sandbox is not a security boundary. Bypasses: absolute executable paths, shell builtins, agent auto-run config that skips permission prompts, macOS absence of exec interception.

Recommended implementation:
- Add `[agents.acp_v2] command_route = "direct" | "ee-mcp"` (default direct; ee-mcp for mediated mode) and `require_process_sandbox` (default false).
- Extend `V2CommandPermission` in `crates/ee-cli/src/app/agent_bridge/app_trust.rs` with `RedirectToMcp`.
- `app_events.rs::present_permission`: on `RedirectToMcp`, select a reject option, emit an auto-resolved audit event, push a system notice telling the agent to use `ee_terminal_create`, never spawn a host terminal.
- Reuse existing MCP-over-ACP advertisement and `ee_terminal_create`; ensure the ACP v2 proxy profile exposes the terminal tools.
- Optional: if `[agents.sandbox] mode = "workspace-write"` is active, allow validated in-workspace direct commands under `v2_command_permission` (process-level containment), with network caveat.
- Doctor/trust status: report route, process-sandbox mode, and the exact limitation that only the process sandbox enforces when the agent skips permission prompts.
- Do not implement Linux ptrace/seccomp exec rewriting or PATH shims as a claimed security boundary.

Tests: v2 command permission Redirect/Allow/Deny/Ask matrix; auto-reject emits notice and no terminal spawn; MCP terminal sandbox; doctor/status; gated process-sandbox integration.

## 2. MCP terminal route (deferred)

Current gap:
- `pump.rs` builds `ee_terminal_create` with `json!({})`, so audit/preview lacks the command.
- `app_decision.rs::resolve_approval` terminal branch calls `spawn_trusted_terminal(..., sandboxed: false)`.
- Default `[agents.terminal_sandbox] mode = "granted"`; MCP server-execute grant therefore auto-allows unsandboxed.
- `terminal_execution_trust_eligible` correctly refuses `prompt.mcp.is_some()`; keep that authority boundary.

Implement shared containment (not cross-route authority):
- Mark MCP-origin terminal prompts (use `prompt.mcp.is_some()` or a `TerminalRoute` field).
- Pass sandbox intent through `resolve_approval` and `resolve_persistent_allow`; apply `terminal_sandbox_spec` to MCP terminal creates in auto-grant and user-approved paths.
- On probe unavailable: `on_unavailable = "deny"` already denies; with `"prompt"`, do not auto-run MCP unsandboxed. Skip MCP server auto-grant and show UI, or fail closed.
- Include `{command,args,cwd}` in the MCP invocation identity for audit and persistent deny matching; server grant matching remains tool/schema based by design.

Optional one-way cross-route authority:
[REDACTED] Config `[agents.mcp] workspace_terminal_trust = "separate" | "acp_proxy"` default separate.
- `acp_proxy` only for server `ee`, transport `McpAcp`, local ACP route, workspace trusted + execute granted + validated invocation; never stdio/external MCP.
- Never let MCP execute grant auto-allow native ACP v1 `terminal/create`.
- Precedence: explicit deny > MCP server execute > workspace execute (if enabled) > prompt; audit records source.

Tests: MCP auto-granted terminal runs in bwrap/Seatbelt and cannot write outside; MCP user-approved honors mode=all; probe-unavailable path; no stdio/workspace authority leak; audit contains command.
