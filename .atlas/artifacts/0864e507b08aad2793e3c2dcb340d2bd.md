# MCP server-level trust assessment (2026-11-24)

Question: add MCP/server trust after workspace trust so all tools/resources from one MCP server are trusted instead of per-tool approval.

Verdict: sound only as a scoped, pinned capability grant. Blanket "trust server = allow every current and future tool" is not safe.

Current state:
- Workspace trust is host-local per canonical workspace (`crates/ee-cli/src/workspace_trust.rs`). It gates workspace `secret:[REDACTED] refs, always-allow candidate generation, and matching of unbounded allow rules (`App::gated_trust_document`, `crates/ee-cli/src/app/agent_bridge/app_trust.rs`).
- MCP allow rules are exact invocations: server + transport identity + tool + schema version + canonical JSON args (`McpRule`, `crates/ee-cli/src/policy/rules/mod.rs`, matcher in `rules/evaluate.rs`). Only `ee_apply_code_action`, `ee_format_file`, `ee_rename_symbol` are eligible (`crates/ee-mcp/src/classify.rs`).
- Bulk MCP read trust already exists: fixed app-owned `ee_mcp_safe_read` profile covers 35 read tools across `stdio:ee --mcp-proxy` and `acp:ee`, granted by `ee do agent trust grant` with 30d/10k budget (`policy/profiles.rs`, `trust_cmd.rs`). It is a finite rule, so `gated_trust_document` does not drop it when workspace trust is untrusted; only `workspace_enabled` matters. This is an inconsistency to resolve if server trust must sit under workspace trust.
- ee proxy exposes tools only, no MCP resources.
- External `[mcp.servers]` entries are forwarded to ACP agents; ee hosts health/discovery/browsing only (`app/agents_mcp/mod.rs`). External tools default to conservative write+overwrite classification and `host_approval=false` (`agent-orchestrator/src/mcp/policy.rs`, `mcp/manager.rs`), so editor trust-store rules do not gate them. External MCP resource tools (`list_mcp_resources`, `read_mcp_resource`, `watch_mcp_event`) are orchestrator read-class tools with no per-tool approval (`mcp/resource_tools.rs`).

Main risks of blanket server trust:
1. Server id is config data, merged across layers. A workspace `.ee.toml` can repoint a trusted id to another command/URL. Grant must bind canonical transport fingerprint, not id.
2. Tool list/schema can drift. `tools/list_changed` and new tools would inherit trust. Pin names + input-schema digests + side-effect classes; any change invalidates grant.
3. External server annotations are untrusted; do not use `readOnlyHint` to authorize. Orchestrator already defaults unknown external tools to write-overwrite.
4. Per-tool approval protects against prompt-injected misuse of an otherwise trusted server, not against malicious server code. A stdio server already runs with user privileges; server trust is not a sandbox.
5. Resources are data and already bypass per-tool approval. Broad resource trust adds little; keep untrusted-content labels and byte/URI caps.
6. External agent-native MCP calls never reach the editor trust store. Enforcing server trust there requires routing calls through ee-agent-host or sharing grants with the orchestrator.

Recommended model:
- Outer: workspace trusted.
- Middle: host-local `McpServerGrant` per workspace with server id + canonical transport fingerprint (stdio command/args/cwd, HTTP URL; env/header names + secret-reference names, never values), pinned manifest digest, capability mask.
- Tier read: all pinned read tools + resources (URI prefixes/exact URIs, bounded).
- Tier write: explicit pinned write tools only, plus workspace-contained target paths, protected-path/secret-store exclusions, existing size caps. No implicit tool expansion.
- Execute: never granted at server scope; terminal/command trust stays separate.
- Precedence: safeguards/deny/mandatory confirm > server grant > fallbacks. Grant cannot override `McpDenyRule`/`ToolRule`.
- Invalidate/drop grant on workspace untrust, server config change, manifest/schema change, or server version change.
- UI/CLI preview must show exact tools, categories, resources, fingerprint, invalidation rules. Default prompt option should be read-only; write grant needs a second explicit confirmation.
- v1 scope ee proxy only unless external tool call routing is added. Do not claim external server trust works before an enforcement point exists.
