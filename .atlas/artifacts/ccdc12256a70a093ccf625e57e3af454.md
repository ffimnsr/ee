## MCP terminal-execution opt-in — 2026-11-24

### Design
General MCP server trust remains read/write only. Terminal execution requires a separate explicit opt-in, because it runs arbitrary commands.

### Changes
- `policy/mcp_server_trust.rs`
  - `McpServerToolGrant::validate`: Execute category allowed only for `ee_terminal_create`; other execute pins rejected.
  - `pinned_execution_tools(transport)`: one `ee_terminal_create` Execute pin when the manifest supports the transport.
  - `McpServerTrustCandidate.execution: bool`; `for_execution_invocation` builds the server grant + execute pin and its own preview.
  - `McpServerGrant::includes_execution`, `preserve_execute_pins`.
- `mcp_trust.rs`
  - `add_grant` preserves Execute pins when re-granting from a non-execution prompt.
  - `revoke_execute` removes only Execute pins, preserving the rest.
  - `ee do mcp trust grant --execute` and `revoke --execute`.
  - Status prints `execute=true|false`.
- Approval UI
  - New `ApprovalChoice::AllowServerExecution`, label `Trust MCP server + terminal (run commands)`.
  - Terminal prompts attach `McpInvocation` for `ee_terminal_create` and offer the execution candidate only when `command_invocation_for_request` validates the command.
  - `resolve_server_trust_choice` persists and dispatches via `resolve_approval(AllowOnce)`, so terminal spawn works.
  - General server-trust fallback now includes `TerminalCreate`, but only matches a grant with the Execute pin.
- `server_trust_prompt_eligible` for TerminalCreate requires validated argv/cwd; shell wrappers and external cwd stay explicit even after execution trust.
- Built-in terminal safeguards, persistent command deny, mandatory confirm, session deny, and workspace gate still outrank execution trust.

### Boundary
- Execution opt-in covers only `ee_terminal_create`, only validated argv/cwd, only while workspace trusted.
- `--execute` grant extends the same server grant; `revoke --execute` removes just the execute pin.
