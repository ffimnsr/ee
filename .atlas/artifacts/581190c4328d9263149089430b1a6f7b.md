Review of docs/FINDINGS.md selected items against current code.

Verified:
- Finding 2 (no classifier verdict cache): correct. `ApprovalClassifier` has only backend + timeout; `ToolExecutor::execute` calls `classify` for every `host_approval || classifier_eligible` call. 5 s is the default timeout, not a guaranteed per-call cost. Suggested key is partly wrong: `OperationIdentity`/`approval_fingerprint` live in ee-cli, not the orchestrator, and `OperationIdentity` does not carry cwd. A cache must key on the exact `ApprovalCandidate` (tool, side-effect class/subclass, redacted bounded args) plus model id and classifier prompt/schema version, run hard blocks first, cache only AutoApprove, and use a short TTL/bounded LRU. Host workspace/rule changes do not need to invalidate it because the host gate re-runs every dispatch.
- Finding 3 (no promotion path): partly correct. There is no classifier feedback loop from host user answers; `DecisionLog` records classifier decisions only. But `Allow always` already creates a persistent `TrustRule` and reduces future prompts, and `Allow session` covers the session. Proactive promotion after N manual allows is optional UX, not a correctness gap.
- Finding 8 (unversioned session keys): fact correct, priority low. `SessionPolicy` uses `BTreeSet<(String, String)>`; fingerprints carry category prefixes but no schema version. State is in-memory and cleared on teardown, so there is no migration problem. A typed key/schema version is hygiene, and would also remove ambiguous `write-batch` path joins.
- Finding 5 (write prompts show no diff): correct. `ApprovalPrompt::write` detail is `path (N bytes)`; `ApprovalKind::Write` stores new content, but `ui/composer.rs` renders only `approval.detail`, and `WriteExpectation` is not rendered. Chat tool details show only `diff: path` / `diff: new file path`, not hunks. `PreparedWrite` has only new content; a diff preview needs a safe baseline read for existing files, bounded hunk lines, `MustNotExist` => creates file, `ExpectRevision` => replaces revision X, and an expand path. `write.rs::diff_hunks` is used for applying edits, not for the approval prompt.

Likely incorrect:
- Finding 4 (approval modes do not propagate): current ee subagents run in-process with the parent `ClientBridge`, and `SUBAGENT_SESSION` only labels internal updates. Host approval lookup uses the parent ACP session id, so the parent `ToolApprovalMode` applies. No OpenCode-managed separate ACP session path was found. Propagating host approval mode through ACP session config would let the agent influence host approval policy and is the wrong mechanism. If a future child ACP session exists, inherit the host mode by parent-session mapping in ee-cli.

Recommendation:
- Implement finding 5 when write-preview UX is in scope.
- Treat finding 2 as a performance optimization.
- Do not implement findings 3, 4, or 8 as written without a separate design decision.
