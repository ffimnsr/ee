# Headless agents memory defaults enabled

## Problem
`ee do agent serve` and `ee do agent mcp` build `RemoteHostConfig` through `crates/ee-cli/src/serve_cmd.rs::build_host_inputs`, which left `RemoteHostConfig::workspace_memory` at the library default (`WorkspaceMemoryHostConfig::default()` -> `enabled: false`). The editor path already enabled workspace fact memory by default, so headless agents disagreed with editor agents mode.

## Fix
- Added `WorkspaceMemorySettings::to_host_config(trusted_roots)` in `crates/ee-cli/src/config/workspace_memory.rs`, mapping merged `[agents.workspace_memory]` settings (enabled, quotas, busy timeout, retention) into `WorkspaceMemoryHostConfig`.
- Reused it in `crates/ee-cli/src/app/agent_pane/app_host.rs`, removing the duplicated editor-only mapping.
- Wired it into `crates/ee-cli/src/serve_cmd.rs::build_host_inputs` with canonical `--allow-root` roots, so `agent serve` and `agent mcp` now enable memory by default and still honor `enabled = false`.

## Validation
- `cargo check -p ee-cli --quiet` passed.
- `scripts/run-tests-memguard.sh cargo test --quiet -p ee-cli config::tests::workspace_memory` passed (8 tests).
- `cargo clippy -p ee-cli --quiet --all-targets -- -D warnings` passed.
- `cargo fmt --all -- --check` passed.
- Added regression test `workspace_memory_host_config_is_enabled_by_default_and_honors_disable`.

Semantic workspace memory (`WorkspaceSemanticMemoryConfig`) remains disabled by design because it needs an injected embedding adapter; it is distinct from durable workspace fact memory.
