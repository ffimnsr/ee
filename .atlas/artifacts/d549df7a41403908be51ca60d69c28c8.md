## MCP server trust second pass — 2026-11-24

### Problem found
Server grant was wired into the evaluator, but only 3 exact-trust tools carried `McpInvocation` into approval prompts (`ee_apply_code_action`, `ee_format_file`, `ee_rename_symbol`). Content writes, filesystem ops, and workspace-memory mutations had no MCP identity, so a granted server still prompted per tool. `resolve_server_trust_choice` also used `dispatch_write_prompt`, which cannot dispatch filesystem/memory prompts.

### Changes
- `policy/mcp_server_trust.rs`: `pinned_server_tools` now covers all manifest Read tools (approval `none`, no ExternalNetwork) and all Write tools, mapping filesystem create/copy to `WriteCreate`, delete to `Delete`, others to `WriteModify`. Execute and external-network tools stay excluded. Delete pins are allowed. Candidate creation requires the invoking tool to be covered.
- `app_proxy.rs` / `pump.rs`: attach path-only `McpInvocation` to content writes (`ee_replace_text`, `ee_apply_patch`, `ee_create_text_file`, `ee_overwrite_text_file`, `ee_write_text_file`), filesystem mutations, and workspace-memory mutations (proxy + `BridgeUiMessage::WorkspaceMemoryApproval` via `ProxyRoute::AcpNative`).
- `app_trust.rs`: exact-trust writes keep MCP identity; content writes keep native write identity so existing write/session/deny rules still match. Added `mcp_server_trust_allowed` gate to the evaluator input.
- `app_approval.rs`: fallback for `Write`/`WriteBatch`/`Filesystem` when native evaluation confirms and the separate MCP operation matches a server grant; then emits `McpServerAllow`. Memory approvals auto-dispatch only on `McpServerAllow`; explicit denies still deny.
- `app_decision.rs`: `AllowServer` handled before the workspace-memory bypass; `resolve_server_trust_choice` now calls `resolve_approval(AllowOnce)` so filesystem/memory prompts dispatch correctly. `server_trust_prompt_eligible` keeps write safety maxima.
- `approval_always.rs`: exact `Allow always` only for exact-trust tools; native write-prefix always restored for content writes; Filesystem/Memory offer server trust; server candidate requires eligible invocation.
- Docs updated: README, CHANGELOG, ISSUES.

### Boundaries
- Covered after grant: pinned reads, exact edits, content writes, filesystem create/copy/move/delete, workspace-memory mutations.
- Still explicit: terminal execution (`ee_terminal_*`), external network (`ee_web_*`, fetch), workspace-memory export, over-cap content writes, unpinned tools, untrusted workspace, persistent denies, mandatory confirms, safeguards.
